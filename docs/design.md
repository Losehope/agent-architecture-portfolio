# 设计文档

## 目标

1. 常见问题走便宜、可预期的路径，模型只在确定性路径解决不了时介入。
2. 数字不能由模型编造。
3. 对外输出必须经过确定性检查，检查失败时拒答，不放行。
4. 慢的外部 Agent 不能拖住用户，也不能让用户收到两条互相矛盾的回复。

## 关键决策

### 1. 先规划，再执行；规则只做先验
- 选择：模型输出 plan（`{"intents":[{"kind":...}]}`），代码按白名单 `lookup|pack|qa|external` 校验、去重。
- 关键词规则只在模型报错或输出无效时使用，不覆盖合法的 plan。
- 理由：关键词路由在多意图问题上容易漏掉另一半；让模型判断、代码兜底边界，可测且可解释。
- 代价：多一次模型调用。规划提示词短，可用小模型。

### 2. 每个臂是漏斗：先确定性，后模型，最后澄清
- lookup：L1 查表 → L2 有界工具循环 → 列出可选项。
- packs：L0 精确 → L1 模型导航（线程加超时）→ L2 澄清卡片。
- 理由：L1/L0 覆盖多数问题，延迟低、零成本；模型只处理残余，且有轮数和时限上界。

### 3. 数字守卫
- L2 的最终答案里出现的数字，必须出现在工具结果中，否则丢弃。
- 理由：工具循环里最常见的错误是模型“顺手”补一个数。

### 4. 用于排序但不展示的字段
- 查表结果按 `spend_share` 排序，但输出列不含该字段。
- 理由：排序需要权重，披露不需要。守卫也会再删一次同名列，两层互相独立。

### 5. 外部专家：回执 + 草稿 + 单条融合
- 立即返回回执，避免用户等待。
- 本地先合成草稿并暂存，截止时间到仍无专家答复就发草稿。
- 专家答复到达时，把草稿与答复融合成一条消息发出，避免两条回复口径不一。
- 去重靠 `_claim`：对同一 ref 只有第一个调用者能发送；之后到达的答复作为 `late_update`。
- 专家抛异常不做重试，由截止时间兜底。

### 6. 守卫：确定性、失败即拒答、改写前后各一遍
- 删除敏感列、整张名单表、命中敏感模式的句子；再 `verify()` 复查。
- 有残留、结果为空或抛异常，一律返回固定拒答文案。
- 融合前对草稿和专家答复各做一次 `redact()`，融合后再做一次完整 `process()`。
- 理由：改写模型可能把被删掉的信息重新带回；只检查输入不够。

### 7. 模型可替换，离线可跑
- `LLM` 是只有一个 `complete(system, user)` 的协议。
- `MockLLM` 按提示词开头的 `[task:xxx]` 标签返回确定结果，测试与演示不需要网络。

### 8. QA 臂：轻型 RAG 与重型 RAG 两级
- 选择：先走**轻型 RAG**——向量、BM25、关键词三路召回，用 RRF 融合后取 top-k，单跳、低延迟；
  置信度足够就直接回答并附来源。未命中或低置信时升级到**重型 RAG**——查询改写 → 重排 → 多跳检索 → 多篇合并。
- 理由：三路召回同时覆盖语义相似与字面命中两类问题，RRF 只依赖排名、不需要训练融合权重；
  重型链路只处理残余问题，成本和延迟可控；升级阈值可观测、可调，便于用 Badcase 校准。
- 代价：轻型链路也要维护向量索引，并保证三路召回的分词、过滤与 top-k 口径一致；
  阈值偏松会过度升级，偏紧会漏掉该升级的问题。

## 已知限制

- 守卫是正则与列名规则，召回受规则覆盖限制。新的敏感表达需要补规则。
- 句子切分按英文标点，中文标点需要调整 `redact()` 的切分表达式。
- 本仓库 demo 只实现关键词重叠（轻型 RAG 的退化版）：没有向量索引、BM25、RRF、重排与多跳检索。
  图中两级 RAG 是生产链路设计，接入时需要补索引、融合、重排器与阈值评估。
- 草稿暂存在内存，进程重启会丢；生产需要持久化队列。
- 融合模型的失败只回退到草稿，没有对融合结果做事实一致性校验。
- 测试用 MockLLM 验证流程，不衡量真实模型的规划质量。

## 测试覆盖

守卫（列、名单表、长间隔敏感句、失败即拒答）、规划（白名单、去重、异常回退）、各臂的层级、
投递（单次发送、超时、改写输出被守卫、改写失败回退草稿）、端到端（同步、异步融合、专家故障）。
